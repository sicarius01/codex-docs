# 이론 학습 V1 외부 평가에 대한 검토 의견

작성일: 2026-09-10

검토 대상: [공개 V1 명세의 고정 버전](https://github.com/sicarius01/codex-docs/blob/ec4df021d1702eb488e01f0265897708fedab926/cognitive-architecture/theory-learning-v1-spec.md), commit `ec4df021d1702eb488e01f0265897708fedab926`.

이 문서는 제공받은 외부 LLM 평가와 해당 명세를 대조한 의견서다. 아래 제안은 채택된 요구사항이나 구현 완료 보고가 아니다. 이 검토를 위해 기존 스펙을 변경하지 않았으며, 미게시 상태의 후속 편집을 공개 명세의 기능으로 간주하지 않았다. 다음 방향은 사용자 피드백 후 결정한다.

**평가의 핵심 문제의식에는 동의한다. 현재 명세는 근거를 잘못 승격하지 않는 규칙보다, 이론을 실제로 시험하고 판단을 바꾸는 절차가 덜 구체적이다.** 다만 반증 경로가 전혀 없다는 결론, 같은 PI 코어를 같은 모델로 해석한 부분, 제시된 몇 가지 해결책의 충분성에는 동의하지 않는다.

현재 설계의 가장 큰 공백은 에이전트 수가 아니라 **주장의 종류·적용 범위·반대 결과·관측 수단·후속 판단을 연결하는 계약**이다. 이를 정하지 않고 리뷰어 모델이나 논리 연산자만 늘리면, 기록과 검토 문장은 늘어도 실제 학습은 약할 수 있다.

## 반증 압력: 도구의 개수보다 주장과 관측의 연결이 문제다

원문 F1은 사용자 피드백과 실제 도구 결과를 기록하고, F4는 로컬 코드·자료 분석·통제 실험을 요구한다. F5는 다음 사용 결과를 다시 검토하도록 한다. 따라서 외부 결과가 들어오는 통로가 아예 없지는 않다. 또한 PI를 기반으로 한다는 사실만으로 학습 대상이 코딩 교훈에 한정되는 것도 아니다.

Jupyter는 실행 수단이다. 로컬 테스트, 저장된 실제 측정 자료 분석, 여러 과제의 결과 비교 모두 커널에서 수행할 수 있다. 반대로 웹 도구를 추가했다고 관측이 자동으로 독립적이거나 인과적으로 유효해지지는 않는다. 중요한 것은 시험 환경과 자료가 이론의 결론을 미리 가정하고 있지 않은가다.

그럼에도 지적은 실질적이다. 현재 명세에는 다음 연결이 충분히 정해져 있지 않다.

| 주장 예시 | 판단을 바꿀 수 있는 근거 | 그 근거만으로 주장할 수 없는 것 |
| --- | --- | --- |
| 조건 X에서 빌드가 실패한다 | 고정된 코드·의존성·환경에서 조건을 바꾼 실제 실행 | 다른 버전·환경에서도 항상 실패한다는 일반화 |
| 방법 A가 B보다 효율적이다 | 정의된 과제 묶음에서 성공·오류·호출·시간을 비교한 결과 | 한 사례의 성공으로 모든 과제에서 우월하다는 결론 |
| 사용자가 형식 Y를 선호한다 | 특정 상황의 명시적 요청·수정·반복된 선택 | 침묵이나 한 번의 지시로 영구적·보편적 선호를 확정하는 것 |
| 관측된 패턴의 원인은 X다 | 경쟁 설명의 예측이 갈리는 관측 또는 통제 실험 | 이론대로 만든 모사 코드가 같은 결과를 냈다는 사실만으로 현실의 원인을 확정하는 것 |

**검토 의견:** 이론을 제안할 때 반대 결과, 그 결과를 얻을 수단, 필요한 추가 조건, 현재 시험 가능 여부를 함께 제시하는 것이 우선이다. 시험할 수 없는 이론의 보류는 정상 결과다. 문제는 무엇을 기다리는지도 모르는 보류가 끝없이 쌓이는 것이다. 채택률을 높이는 것이 학습의 성공 지표가 되어서는 안 된다.

10.2의 통제된 예시는 기능 연결 시험으로는 적절하다. 원문도 이를 범용 개선의 증명이라고 하지 않는다. 다만 이것만 통과해서 실용적인 반증 루프까지 검증됐다고 볼 수는 없다. 후속 시험 후보로는 틀린 후보의 기각, 그럴듯하지만 시험 불가능한 후보의 보류, 혼입 요인 때문에 결론을 좁히는 사례가 필요하다. 이는 검토 제안이며 이번에 수용 기준을 변경한 것은 아니다.

## method 이론: 검증 수단은 있지만 개별 이론으로의 환류가 불명확하다

F5는 사용 결과의 예측·관측·실패·비용을 이론 수정본에 연결하고 다음 검토에서 판단하도록 한다. 10.3도 방법 가설의 사용 결과를 측정한다. 따라서 사용 횟수를 강화 근거에서 제외했다고 성과 근거까지 없어지는 것은 아니다. “많이 썼다”와 “비교 가능한 조건에서 결과가 개선됐다”는 다른 정보다.

다만 어떤 방법을 어느 기준 방법과 비교하고, 비교 결과가 어떤 수정본의 어느 적용 범위를 지지하는지는 부족하다. “분포 전체에서 A가 우월하다”는 주장에 한 사례는 충분하지 않지만, 한 사례도 좁은 조건의 반례나 후속 시험의 근거가 될 수 있다.

외부 평가가 제안한 두 선택지, mini-eval 도입 또는 V1에서 모든 method의 보류 고정은 유일한 선택지가 아니다. 좁은 적용 범위로 잠정 사용하면서 실제 실패·비용을 수집할 수도 있다. 단, 이 경우에도 검증된 성과와 탐색 중 가설을 표시상 구분해야 한다.

**검토 의견:** 소규모 비교 실험을 기존 F4 조사의 한 방식으로 구체화하는 안이 가장 자연스럽다. 별도 에이전트나 팀의 LLM judge를 새로 만드는 요구는 아니다. 예를 들어 다음 항목을 정할 수 있다.

- method 수정본과 적용 조건, 비교할 기준 절차, 시험 전에 고정한 결과 지표.
- 조건을 맞춘 과제별 결과·비용·실패, 사용한 모델·입력·도구 설정.
- 어떤 결과면 적용 범위를 좁히거나 방법을 수정·보류할지에 대한 사전 기준.
- 해당 방법을 검토하는 개발용 과제와 최종 성능 평가용 과제의 분리.

F4의 반복 시험에 최종 평가 과제를 사용하면 그 자체로 평가에 적응하게 된다. 방법별 조사 루프와 최종 A/B/C 평가의 데이터 경계도 함께 정해야 한다. 작은 비교 실험만으로 넓은 분포의 우월성을 입증했다고 해서는 안 된다.

## 모델 분리와 채택 조건

### 같은 코어가 같은 모델이라는 뜻은 아니다

원문 4절의 같은 PI 코어는 공통 런타임 사용을 뜻한다. 4.2절의 역할 실행 메시지에는 모델 설정이 있고, 13절은 제공자·모델을 확정할 항목으로 남긴다. 명세에서 세 역할이 반드시 같은 모델이라고 결론 내릴 근거는 없다.

동일 모델을 쓴다면 프롬프트를 나누어도 오류가 상관될 수 있다는 우려에는 동의한다. 다른 모델을 쓰더라도 같은 자료, 같은 잘못된 전제, 비슷한 학습 경험에 의존할 수 있다. 모델 다양화는 하나의 실험 변수이며 독립적인 실증의 대체물이 아니다.

**검토 의견:** 3개 논리적 역할은 유지 가능한 출발점이다. 별도 문맥, 역할별 책임, 원자료 조회, 실제 검사를 먼저 연결하고 실패 자료를 보고 모델 조합을 판단하는 편이 맞다. 이번 평가만으로 에이전트 수나 제공자를 늘려야 한다는 결론은 나오지 않는다.

### 비논리적 증거 1건이라는 필수 조건은 보완이 필요하다

원문은 증거 종류를 구분하지만 아직 구현된 타입 검사나 상태 전이 코드가 없다. 설령 스키마가 `executed_test`라는 값만 허용하더라도, 실제 실행이 있었는지와 그 실행이 주장을 시험했는지는 별도로 확인해야 한다. 외부 평가의 긍정적인 표현도 이 점에서는 한 단계 앞서 있다.

평가자는 이를 충분조건이 아니라 최소 필요조건으로 제안했다. 경험적 주장에 무근거 채택을 막는 장치로는 의미가 있다. 다만 모든 이론에 일률적으로 적용하거나 이것으로 편향 문제가 해결됐다고 판단하기에는 세 한계가 있다.

1. 후보를 만든 관측을 다시 인용하면 개수 조건은 충족하지만 추가 검증은 없다. 기존 자료도 유효한 근거가 될 수 있으나 탐색에 쓴 자료와 확인에 쓴 자료의 역할을 구분해야 한다.
2. LLM이 자기 결론을 그대로 출력하는 코드를 실행해도 실행 기록은 남는다. 검사의 독립성, 측정 대상, 경쟁 설명을 구별하는 능력은 보장되지 않는다.
3. 형식 논리의 조건부 결론이나 증명 가능한 명제에 경험 관측을 일률적으로 요구하는 것도 부적절하다. 검증된 증명과 LLM의 자연어 논리 검토는 구분해야 한다.

**검토 의견:** 채택 기준은 주장 종류와 범위에 맞아야 한다. 경험적 주장은 실제 관련 관측·시험, 방법의 성과 주장은 비교 조건과 결과, 사용자 선호는 해당 상황의 명시적 피드백, 형식적 주장은 검증 가능한 전제·추론에 의존한다. 어떤 경우든 반대 근거와 미해결 제한을 남겨야 한다.

Controller는 필수 필드, 참조의 실재, 실행 상태, 근거 계보, 허용된 상태 전이를 검사할 수 있다. 증거의 관련성과 결론의 범위는 여전히 판단이 필요한 부분이다. 구조적 검사를 통과했다는 사실을 진리 판정으로 표현해서는 안 된다. 동일 원근거의 복제 방지는 필요하지만, 서로 다른 ID를 가진 관측들 사이의 통계적 의존성까지 해결하지는 않는다.

## 평가 설계: 전체 효과 측정과 원인 진단을 구분해야 한다

### A/B/C와 추가 조건 D

A/B/C는 경험 활용 방식별 최종 결과를 비교하는 출발점으로 쓸 수 있다. C가 B보다 나쁘면 해당 표본에서 전체 구성의 이득이 관측되지 않았다는 결과는 얻는다. 일반적인 성능 차이는 불확실성과 함께 판단해야 한다. 또한 이론이 틀렸는지, 필요한 이론을 못 찾았는지, 넣어 준 이론을 Worker가 잘못 적용했는지는 구분하기 어렵다. 이 지적에는 동의한다.

사람이 이론을 고르는 D는 유용한 진단 조건이다. 다만 다음 통제가 필요하다.

- C와 D가 동일한 고정 KB를 사용하고, D는 새 이론을 작성하거나 기존 이론을 고치지 않는다.
- 선택자에게 시험 정답과 실행 결과를 보여주지 않고 과제와 허용된 KB만 제공한다.
- 문맥 길이, 표시 형식, Worker, 시험 예산을 맞추고 선택 절차를 미리 정한다.

이 조건에서 C와 D의 차이는 검색·선택 개선 여지를 살피는 자료가 된다. 그래도 인간 선택이 완벽한 오라클이라는 보장은 없다. **B와 D의 차이는 순수한 이론 품질만 보여주지 않는다.** 정보 표현, 선택 정책, 문맥 내용이 함께 다르기 때문이다. 품질 자체를 보려면 주장별 검증이나 정보 선택·표현을 통제한 별도 비교가 필요하다.

**검토 의견:** D는 우선 작은 진단 표본에 사용할 만하다. 원인 분리가 필요하다는 이유로 V1부터 모든 요소의 조합 실험을 만들 필요는 없다. 단, 진단 조건의 결과를 실제 운영 성능으로 보고해서는 안 된다.

### 표본 수와 불확실성

원문은 여러 과제·반복 실행과 변동 보고를 요구하지만 표본 수, 반복 배치, 최소 관심 효과, 종료 기준은 정하지 않았다. 실제 개선 주장을 하기 전에는 보완해야 한다. 반면 효과가 작을 것이 거의 확실하다는 평가는 아직 측정 근거가 없는 예상이다.

과제별 paired delta와 신뢰구간은 합리적인 후보지만 bootstrap이라는 이름을 넣는 것만으로 통계력이 생기지는 않는다. 같은 과제의 반복 결과, 같은 계열의 변형 과제를 모두 독립 표본처럼 세면 불확실성을 과소평가할 수 있다. 비교 대상을 과제로 볼지 과제 계열로 볼지 먼저 정하고 그 단위의 의존성을 반영해야 한다. 적은 실행 횟수에서 점추정치만 비교하는 위험은 기존 에이전트 평가 연구도 다룬다. 해당 연구는 강화학습 대상이며 이 프로젝트의 효과 크기나 필요한 표본 수를 직접 제공하지는 않는다. [Agarwal 외, 2021](https://arxiv.org/abs/2108.13264)

**검토 의견:** 작은 개발용 예비 실험으로 분산과 비용을 파악한 뒤, 본 평가의 과제·계열 수, 반복 수, 주요 지표, 최소 관심 효과, 분석·종료 규칙을 사전에 고정하는 편이 낫다. 지금 근거 없이 특정 n을 정답처럼 적는 것은 적절하지 않다. 데이터가 부족해 결론을 유보하는 것도 정당한 연구 결과이며, 긍정 결론을 얻으려고 평가를 계속 바꾸는 것이 더 큰 문제다.

### 과제 계열과 오염

과제 분리만으로 먼 전이를 주장할 수 없다는 지적에는 동의한다. 같은 틀에서 이름·숫자만 바꾼 시험과 다른 구조·계열의 시험은 구분해야 한다. 다만 같은 계열의 새 문제에서 경험을 재사용하는 것은 목적에 따라 유효한 근거리 전이 평가이며, 그 자체가 모두 오염은 아니다.

검토할 만한 구분은 개발용 과제, 같은 계열의 미사용 과제, 미사용 계열의 전이 과제다. 계열의 기준도 결과를 본 뒤 유리하게 만들지 않아야 한다. 최종 평가 결과가 다시 이론 추출과 수정에 들어가면 평가 세트를 소진한 것으로 취급해야 한다.

### 개선과 비용의 합격선

원문은 기능 완성과 능력 개선을 분리한다. 따라서 성능 이득이 없더라도 기능 V1은 완성할 수 있다는 기존 원칙은 타당하다. 실용성이 입증됐다는 별도 결론에는 최소 효과와 비용 기준이 필요하다는 비판에도 동의한다.

학습 비용이 5배이고 정확도가 2% 높다는 정보만으로는 판정할 수 없다. 2%가 상대 변화인지 퍼센트포인트인지, 학습 비용이 몇 번의 재사용에 분산되는지, 추론 비용과 오류 비용이 어떤지가 필요하다. 이번 의견서에서 임의의 합격선을 정하지 않는다. 사용 목적을 정한 뒤 기능 통과, 성능 근거, 비용상 실용성을 별도 기준으로 판단하는 것이 맞다.

## KB 성장과 중복: 작은 V1에도 관리 규칙은 필요하다

단일 실행의 후보 수와 검색 상한만으로 장기 누적을 관리할 수 없다는 지적에 동의한다. 검색량을 고정해 둔 상태에서 KB가 커질 때, 관련 이론 누락과 모순 탐지 누락을 관찰할 수 있어야 한다. 재검토 표시를 붙이는 것과 재검토를 실제로 수행하는 것은 별개다.

검토할 최소 항목은 미검토 후보 수, `held`의 보류 이유·대기 기간, `needs_review` 큐 길이·최고 대기 시간, 새로운 근거 도착 여부, 실행당 큐 처리 예산이다. 신규 생성보다 중요한 기존 의존 이론의 재검토가 밀리는지도 봐야 한다. 원문에 있는 작은 자료의 전수 비교는 검색 누락을 진단하는 출발점이 될 수 있다.

다만 `held` 비율을 줄이거나 기각 건수를 늘리는 목표는 피해야 한다. 보류와 기각은 근거의 결과여야 한다. backlog 상한에 도달했을 때 신규 생성을 늦출지, 수동 검토를 요청할지, 활성 목록에서 보관 목록으로 옮길지는 별도 정책 선택이다. 과거 근거를 자동 삭제해야 한다는 결론은 아니다.

중복 처리도 보완할 필요가 있다. 원문에는 기존 수정본 참조와 범위가 다른 주장의 분리 원칙이 있어 아무 처리도 없는 것은 아니다. 그러나 의미가 같은 후보를 기존 이론의 새 근거로 합칠지, 별도 이론으로 남길지에 대한 규칙은 약하다.

`duplicate_of`, `refines`는 가능한 표현이지만 새 관계 이름 자체가 해결책은 아니다. 같은 이론의 수정본, 정확한 중복, 범위를 좁힌 별도 주장, 실제 경쟁 설명을 구분하는 병합 정책이 우선이다. 자동 유사도만으로 합치면 중요한 적용 조건이 사라질 수 있다. V1에서는 기존 후보 검색 후 Integrator가 병합·분리 이유와 원근거를 보존하는 안부터 검토할 수 있다.

## 실무 지적의 정확성과 보완 범위

| 항목 | 검토 의견 |
| --- | --- |
| Windows JSONL·CRLF | 전송 계약을 구체화하자는 제안에는 동의한다. 다만 JSON Lines는 CRLF도 허용하므로 CRLF 존재 자체가 오류는 아니다. UTF-8, 프레이밍, 청크 중간의 다중바이트 문자, EOF 중간 메시지, 최대 바이트 수를 시험하는 것이 핵심이다. [JSON Lines](https://jsonlines.org/) |
| binary 모드 | 개행·인코딩 변환을 직접 통제하는 적절한 선택이다. 명시적으로 설정한 텍스트 스트림도 가능하므로 유일한 구현은 아니다. 코드 안 줄바꿈은 JSON 문자열로 escape하고 프로토콜 줄바꿈과 구분해야 한다. [Python IO](https://docs.python.org/3/library/io.html) |
| handshake | 버전 불일치와 기능 지원 여부를 실행 전에 검출할 필요가 있다. 단일 버전 V1은 복잡한 협상 대신 고정 버전 확인과 불일치 거부로 시작할 수 있다. 모든 메시지의 공통 envelope와 요청 연결 규칙은 정하는 편이 좋다. |
| 취소 경합 | 동의한다. 중단 요청, 실제 중단, 결과 수신, 결과 저장 상태를 구분해야 한다. 취소가 먼저 요청됐어도 실제 완료한 결과를 삭제하거나 이미 일어난 부작용을 없었다고 처리해서는 안 된다. |
| 실행 전 dedup 기록 | 필요할 수 있지만 이것만으로 멱등성이 해결되지는 않는다. 아래의 결과 불명 구간을 다뤄야 한다. |
| SQLite | 원문에 Controller 단일 쓰기와 트랜잭션 원칙은 있다. 구체적인 writer 소유권·연결·잠금 정책은 부족하다. GUI 조회와 쓰기를 함께 운영한다면 WAL과 제한된 busy timeout은 적절한 후보이나, 오류 처리와 내구성을 대신하지 않는다. [SQLite WAL](https://www.sqlite.org/wal.html), [busy_timeout](https://www.sqlite.org/pragma.html#pragma_busy_timeout) |

실행 전 `call_id`를 저장해도 다음 두 상황은 구분하기 어렵다.

```text
실행 의도 저장 → 실제 실행 전 프로세스 종료
실행 의도 저장 → 실제 실행 완료 → 결과 저장 전 프로세스 종료
```

둘 다 저장소에는 결과가 없는 요청으로 보일 수 있다. 무조건 재실행하면 두 번째에서 부작용이 반복되고, 무조건 완료 처리하면 첫 번째에서 실행이 누락된다. DB의 기록과 임의 커널 코드의 외부 효과는 하나의 트랜잭션으로 묶이지 않는다.

**검토 의견:** 요청을 유일하게 식별하는 키와 인자 해시, 실행 의도와 결과 저장을 분리하고 결과 불명 상태를 남겨야 한다. 완료 결과가 있으면 재반환하고, 대상 도구가 멱등 키나 결과 조회를 지원하면 이를 사용한다. 확인할 수 없는 실행은 자동 재실행하지 않는 정책이 필요하다. 이는 기존 원칙을 구현으로 연결하는 문제이며 exactly-once 보장으로 표현할 수 없다.

SQLite의 단일 writer도 모든 스레드가 하나의 연결 객체를 공유한다는 뜻으로 적으면 안 된다. 쓰기 소유자를 명확히 하고 GUI 읽기 연결의 수명과 트랜잭션을 따로 관리하는 안이 적절하다. WAL은 동시 읽기에 유리하지만 한 번에 하나의 writer라는 제약과 checkpoint 관리가 남는다. [SQLite 동시성](https://www.sqlite.org/wal.html#concurrency)

## 문서 구조와 후속 논의의 우선순위

핵심 명세, Windows 설치 런북, Vetu 조사 자료는 갱신 이유가 다르므로 분리하는 방향에 동의한다. 최초 조사 단계에서 한 문서로 읽게 한 선택 자체가 잘못은 아니지만, 구현 단계에서는 기준 명세가 바뀐 것인지 설치 안내만 갱신된 것인지 구별하는 편이 낫다. 특정 절이 6개월 안에 반드시 낡는다는 식의 시점 예측에는 근거가 없다. 이번에는 기존 문서를 분리하거나 이동하지 않았다.

내가 권하는 논의 순서는 다음과 같다. 이는 작업 착수나 스펙 변경의 결정이 아니다.

| 시점 | 우선 검토할 내용 | 범위를 작게 유지하는 방식 |
| --- | --- | --- |
| 학습 로직 구현 전 | 주장 종류별 시험·반대 결과·채택 범위, method 조사 환류, 근거와 상태 전이 | 기존 3개 역할과 F4 조사 구조 안에서 구체화 |
| 실행 연결 구현 전 | 메시지 계약, 취소·결과 경합, 실행 의도·결과 불명·재개, 쓰기 소유권 | 단일 버전·순차 실행·로컬 환경으로 시작 |
| 누적 학습 실행 전 | 중복 병합 정책, 재검토 큐·대기 기간·처리 예산 | 공통 저장소와 제한된 큐, 전용 Meta Agent 추가 없이 시작 |
| 개선 결과 주장 전 | 평가 과제 범위, 개발/최종 평가 분리, 반복·불확실성, 최소 관심 효과·비용 기준 | 예비 시험 후 본 평가 고정, D는 우선 소규모 진단에 사용 |
| 사용·유지보수 단계 | GUI에서 실제 입력·근거·판단·대기 상태 확인, 명세와 런북 분리 | 같은 기록을 조회하는 화면과 문서 참조를 재사용 |

사용자가 별도로 요청한 Langfuse 학습 조회와 GUI는 여전히 필요한 요구다. Langfuse는 경험을 가져오는 경로이고 GUI는 판단 과정을 확인하는 수단이므로, 어느 쪽도 독립적인 반증을 저절로 만들어주지는 않는다. 반대로 반증 규칙이 좋아도 실제 입력과 근거를 확인할 수 없다면 문제를 진단하기 어렵다. 두 요구와 이번 비판은 함께 검토할 대상이며, 이 의견서가 후속 스펙 결정을 대신하지 않는다.

이 평가를 받아들여 가장 먼저 명확히 할 질문은 **“이 이론이 틀렸다면 어떤 결과를 보게 되며, 지금 시스템은 그 결과를 어디서 어떻게 얻고, 얻은 뒤 무엇을 바꾸는가?”**다. 이 연결을 구체화하는 데는 동의하지만, 에이전트·도구·평가 조건을 모두 한꺼번에 늘리는 것이 답이라고 보지는 않는다.
