# Data Service 실행 설계

공개 열람본 · 함께 읽기: [데이터 조사·무료 범위](crypto-data-landscape-2026-09-15.md) · [M1 API](api.md) · [다음 단계 제안](#next-phase)

작성: 2026-09-15, 검증·다음 단계 제안 갱신: **2026-09-16 KST**. Full Trading 내부 독립 레포·프로세스 방향과 첫 구현에 대한 사용자 지시를 반영한다. M0·M1은 구현 결과이고, M1.1 이후는 아직 구현하지 않은 계획이다.

## 1. 목표와 이번 작업의 종료점

목표는 무료 정형 비호가·비틱 데이터의 과거·현재를 동일한 데이터 정의와 API로 제공하는 것이다. 전체 서비스는 단계적으로 완성한다. **완료된 첫 구현은 M0 설계와 M1 상품 정보·확정 봉의 수집/저장/조회 및 제한된 검증까지다.** 현재는 사용자가 검토하는 단계다. 9절에 다음 작업을 제안하며 운영 배포나 기존 소비자 전환을 뜻하지 않는다.

| 단계 | 산출물 | 통과 기준 | 상태 |
|---|---|---|---|
| M0 | 원천 계약, 최소 API, 저장 선택, 실행 계획 | 실제 샘플/공식 정의와 설계의 차이를 설명 가능 | 완료 |
| M1 | BTC/ETH USD-M perpetual 상품 정보·확정 1분 봉, 최신/기간 조회 | 정밀도·중복·정정·재시작·페이지 일관성 검증 + 공개 API 소량 검증 | 완료, 아래 검증 범위에 한함 |
| M1.1 | 최신 수집과 과거 복구 분리, 영속 결측 상태, 종목별 관측 | 과거 결측·장기 중단·복구 작업 중에도 최신 수집 지속 | 제안, 미착수 |
| M2 | 확정 펀딩 → OI를 데이터별로 완성 | 현재 snapshot과 원천 기간 통계 분리, 복구/조회 검증 | 미착수 |
| M3 | 준비 작업 API·PIT 시각·자원 예산·장기 운영 강화 | 미보유 이력 준비, 당시 가용성·호출 예산·용량 관리 검증 | 미착수 |
| M4 | 연구 소비자 1개 연결 | 기존 결과와 차이의 원인 설명, 전환/복귀 기준 | 미착수 |
| M5 | 두 번째 거래소·데이터 확대 | 거래소별 지원 범위와 의미를 공통 계약으로 표현 | 미착수 |
| M6 | 필요 시 구독 | 유실/재접속/정정 복구 기준 검증, UDP는 후보 | 미착수 |

M1이 통과해도 전체 서비스가 실거래 운영 준비를 마쳤다고 표시하지 않는다. 검증 시간 경과 자체가 통과 기준은 아니다.

## 2. 독립 컴포넌트와 초기 저장 선택

- `data-service/`는 자체 Cargo 프로젝트와 로컬 Git 저장소다. feeding/bv_sync path 의존을 두지 않는다.
- 수집·저장·조회 모듈을 한 실행파일에 둔다. DB 처리 동안 네트워크 응답을 기다리지 않는다.
- **M1 저장소 채택: 로컬 SSD SQLite, WAL + FULL synchronous, 원본 응답과 불변 revision.** 소수 심볼과 단일 writer에서 트랜잭션·재시작·정정 이력을 검증했다. NAS SMB 위에 DB를 두지 않는다. 대규모 처리량/다중 writer/장기 보관 적합성은 M3에서 실측한다.
- 기존 QuestDB에 표준화·정정 요구를 맞추는 작업과 운영 DB 변경을 첫 구현의 선행 조건으로 두지 않는다. SQL 테이블을 소비자 API로 노출하지 않아 저장 구현은 이후 변경할 수 있다.
- 기본 실행은 loopback HTTP다. 같은 머신의 feeding과 CPU·I/O·거래소/IP quota는 공유될 수 있으므로 요청 대상·한도·동시성을 제한한다.

## 3. M1 데이터·원천

| 데이터 ID | 원천 | 시간 의미 |
|---|---|---|
| `reference.instrument` | Binance USD-M `GET /fapi/v1/exchangeInfo` | 수집 시점의 상품 snapshot. 과거에 같은 규칙이 유효했다고 소급하지 않음 |
| `market.ohlcv.1m` | `GET /fapi/v1/klines`, interval=1m | 봉 시작 시각, UTC 반개구간. `/fapi/v1/time`으로 확인한 원천 시각보다 종료 시각이 이른 확정 구간만 수집 |

상품 키는 venue=`binance-futures`, symbol=`BTC^USDT` 또는 `ETH^USDT`, product=`perpetual`, settlement=`USDT`다. Binance 원천 심볼은 별도 필드다. 가격 precision 값은 tick size가 아니며 PRICE_FILTER/LOT_SIZE의 실제 규칙을 사용한다.

봉의 OHLC·base/quote volume·taker volume은 정확한 ×10^8 정수, API 값은 문자열이다. 체결 수는 정수다. 지원 정밀도를 초과하는 유효숫자·overflow·잘못된 OHLC/시간/음수 값은 수집 오류로 드러내며 반올림하지 않는다.

## 4. 데이터 시간·정정 계약

- `event_time_ms`: 봉 시작 또는 상품 관측 시각. 원천이 공개한 시각과는 다르다.
- `observed_at_ms`: 해당 원천 응답을 실제로 수신한 로컬 시각. 백필을 원천 당시 관측으로 위장하지 않는다.
- `recorded_at_ms`: 로컬 저장 처리 시각. 엄밀한 최초 공개/커밋 완료 시각을 대신하지 않는다.
- `record_id`와 증가하는 `revision`: 같은 봉의 정정 전 값도 보존한다. 동일 레코드의 같은 현재 값 재수집은 새 revision을 만들지 않는다. A→B→A 정정은 별도 세 revision이다.
- `view_seq`: 트랜잭션으로 확정된 저장 revision 경계. 최신·기간 조회 및 여러 페이지를 같은 경계로 고정할 수 있다. 뒤늦은 과거 수집은 event time 기준 최신을 되돌리지 않는다.
- **M1의 view_seq는 재현 가능한 저장 snapshot이다. 벽시계 as_of/PIT의 완전한 대체물이 아니다.** timestamp 기반의 엄격한 PIT 조회는 미지원으로 표시하며 M3에서 공개 시각·조회 가용 시각과 시계 정책을 검증한다. M1에서 원본/관측 시각/버전을 보존하고 정정 전후 snapshot 조회를 검증한다.

## 5. 수집과 조회 동작

- 현재 수집은 기본 두 심볼, 순차 REST 요청, 짧은 중첩 구간으로 마지막 확정 봉을 재확인한다. 마지막 저장 봉 이후 구간은 재시작 시 보충한다.
- 명시적인 과거 보충은 범위·페이지 크기를 제한하고 페이지별로 영속화한다. 실패 후 같은 범위를 다시 실행해 이어갈 수 있어야 한다.
- 네트워크 timeout과 전체 요청 간격, 429/418의 Retry-After 및 과거/현재 수집 간 간섭을 다룬다. 무한 재시도로 API 호출을 누적하지 않는다.
- M1 조회는 **이미 수집된 데이터 조회**다. 요청 중 거래소 대량 수집을 숨겨 실행하지 않는다. 미수집/부분 결과를 명시한다. 자동 준비 작업 API와 영속 작업 스케줄러는 후속 구현이다.
- 최신은 가장 최근 event time의 유효 revision이다. 기간은 `[start_ms, end_ms)`다. 정정 중 pagination도 같은 view를 사용한다.
- 연속 봉의 요청 구간에서 누락을 확인한다. min/max만으로 완전하다고 하지 않는다. 상품 snapshot의 미관측 과거는 완전한 변경 이력으로 표시하지 않는다.
- 최신성은 값이 바뀌었는지가 아닌 데이터 대상 시각으로 판단한다. 거래소 장애 때 이전 값을 지금 받은 값처럼 재라벨링하지 않는다.

## 6. 검증 목록

| 검증 | 기대 결과 | 상태 |
|---|---|---|
| 정밀도·파싱 | 소수 정확 보존, 초과 정밀도/overflow 거부, 미확정/잘못된 봉 제외 | 자동 테스트 + 실제 10봉의 OHLC/거래량/taker/체결 수 원천 대조 통과 |
| 같은 데이터 반복 수집 | 봉 revision/행 수 증가 없음, 첫 관측 provenance 유지 | 자동 테스트 + 실제 10봉 재수집 unchanged=10 통과. 원본 응답과 새로운 상품 관측은 별도 보존 |
| 정정과 snapshot | A→B→A revision 보존, 이전 view에서 이전 값 조회 | 고정 fixture 계약 테스트 통과. 실제 거래소 정정 사건을 관측했다는 의미는 아님 |
| 과거/현재 연결 | latest record를 range로 재조회 가능, 늦은 백필로 최신 역전 없음 | 계약 테스트 + 실제 현재 수집 후 HTTP latest/range 레코드 일치 통과 |
| 페이지 경계 | 중간 정정·백필에도 고정 view에서 중복/누락 없음 | 정정/백필 fixture 테스트 + 실제 5봉을 3페이지로 조회 통과 |
| 저장 오류·재시작 | 원본/레코드 원자성, DB 재오픈 결과 동일, 부분 수집 재시도 가능 | rollback/DB 재오픈/분할 보충 테스트 + commit 완료 후 실제 프로세스 종료·재조회 통과 |
| 결측·지원 범위 | 중간 누락/미수집/미지원/오래된 값 명시 | 계약/API 테스트 + 실제 HTTP의 미지원 as_of=400 통과 |
| 호출 제한·중복 수집기 | 제한 응답 후 재요청 억제, 같은 DB 수집기 충돌 방지 | loopback fixture 429/418 재요청 억제 + 실제 실행 중 두 번째 수집기 거부 통과 |
| 외부 공개 API | 제한된 BTC/ETH 샘플 저장·HTTP 조회·원천 대조 | 2026-09-16 00:02 KST 소량 검증 통과 |

검증 명령: `cargo test --all-targets` **30/30**, `cargo build`, `cargo clippy --all-targets -- -D warnings`, `cargo fmt --all -- --check` 통과. Python 예제 문법/도움말과 실제 HTTP 실행도 확인했다. 저장 계약은 별도 에이전트가 읽기 전용으로 독립 검토했고, runtime은 통합 담당의 코드 검토와 실행 검증을 거쳤다.

실제 검증 로그는 로컬에 보관하며 공개본에는 포함하지 않는다. **M1 검증 종료 당시** 봉 46개(두 심볼 각각 23개), 상품 관측 6개, 원본 응답 9개, 저장 view 7이었다. SQLite `integrity_check=ok`, `foreign_key_check` 오류 없음, WAL 확인. 당시 봉 구간은 UTC `[2026-09-15 14:39, 2026-09-15 15:02)`였으며 검증용 두 서버 프로세스는 모두 종료했다. 이후 사용자 검토 화면에서 사용하는 DB는 추가 수집될 수 있으므로 이 수치를 현재 보유량으로 해석하지 않는다.

**남은 검증:** 전원 손실·저장 transaction 도중 강제 종료·지속 네트워크 장애·장기 연속 관찰·대규모 성능·소비자 연구 결과 비교. 429/418 검증은 제어된 로컬 HTTP fixture이며 실제 거래소의 호출 한도를 일부러 소진하지 않았다. 원천에 영구적인 중간 결측이 있으면 해당 심볼 보충이 멈추는 M1 제한은 M1.1에서 먼저 다룬다. raw/revision 무제한 보존에 대한 용량 관리와 다른 프로세스와의 IP quota 통합은 M3에서 다룬다.

## 7. 작업 분담과 변경 관리

- 공통 계약을 먼저 고정한 뒤 저장/model과 원천/서비스 구현의 파일 소유권을 분리한다.
- 통합 담당이 README·계약·실제 동작을 맞추고 독립 검토자가 수정된 코드를 확인한다.
- 단계별 README 현재 상태와 이 문서 검증 결과를 갱신한다. 코드·프로토콜·성능 주장이 실제 검증보다 앞서지 않도록 한다.
- M0·M1 구현은 로컬 검증 범위였다. 2026-09-16 사용자 요청으로 데이터 조사·실행 설계·M1 API 문서의 공개 저장소 게시를 추가했다. 코드 저장소 커밋·원격 생성·푸시·운영 서비스 변경·기존 데이터 삭제는 포함하지 않는다.

## 9. 다음 단계 제안 — 수집 지속성을 먼저 확보

### 9.1 순서를 조정하는 이유

**추천 순서는 M1.1 수집 지속성 → M2a 확정 펀딩 → M2b OI → M3 준비 작업·PIT·운영 검증 → M4 연구 소비자 연결이다.** 기존 M3의 일부를 앞으로 당긴다. 현재 지원 범위인 Binance USD-M BTC/ETH 두 종목을 유지하면서 단계마다 실제로 확인할 수 있는 결과를 만든다.

현재 수집기는 마지막 저장 봉부터 이어 받으며, 연속 구간 중 봉 하나가 없으면 해당 페이지를 오류로 처리한다. 31일을 넘는 중단도 현재 복구 경로의 한도에 걸린다. 이 상태에서 데이터 종류를 늘리면 각 계열이 같은 이유로 멈출 수 있다. 우선 과거 결측이 남아 있어도 최신값은 계속 들어오고, 결측은 정직하게 보이는 구조가 필요하다.

이번 문서 갱신은 다음 작업의 구상이다. 아래 기능·관측 기간·통과 기준은 아직 실행하거나 달성하지 않았다.

### 9.2 M1.1 — 바로 다음 구현 묶음

사용자가 확인할 결과는 **결측 구간이 표시되는 동안에도 차트 오른쪽의 최신 봉이 계속 늘어나는 화면**이다.

| 작업 | 구현할 동작 | 완료 기준 |
|---|---|---|
| 최신 수집 경로 분리 | 원천 시각 기준 최근 확정 구간을 먼저 요청. 오래된 복구 작업과 진행 위치 분리 | 과거 영구 결측이나 31일 초과 중단이 있어도 최신 조회가 갱신됨 |
| 영속 결측·작업 기록 | dataset/상품/구간별 미수집 범위, 시도 횟수, 다음 재시도 시각, 오류·진행 위치 저장 | 프로세스 재시작 뒤 작업 복구. 성공 저장과 진행 갱신 사이에 잘못된 완료 상태가 생기지 않음 |
| 제한된 과거 보충 | 긴 구간은 한도 내 조각으로 나누고, 한 cycle의 요청 수·시간을 제한 | 큰 백필이 최신 수집의 기회를 소진하지 않음. 동일 구간 요청을 중복 작업으로 누적하지 않음 |
| 오류 격리 | 누락과 잘못된 행을 구분하고 작은 구간으로 재확인. 유효한 인접 구간부터 진행 | 실패 구간을 0/직전 값으로 채우지 않고, 다른 구간·종목 수집은 계속됨 |
| 원천 한도 준수 | 최신·과거 요청이 같은 거래소 cooldown을 준수하며 최신 작업에 우선순위 부여 | 429/418 대기 중 다른 경로로 재호출하지 않음. 재시작으로 알려진 대기시간을 우회하지 않음 |
| 종목별 상태 표시 | 마지막 성공·최신 봉 종료·수집 지연·남은 결측·재시도 사유를 API와 화면에 표시 | 프로세스 정상/데이터 신선함/이력 완전함이 각각 구분됨 |

첫 M1.1에서는 기존 `catalog/query` 조회 의미와 불변 revision을 유지한다. 영속 작업 기록은 먼저 내부 복구에 사용하며 사용자용 준비 작업 API는 M3에서 연다. 다른 프로세스까지 포괄하는 전역 스케줄러나 여러 거래소용 프레임워크는 이 묶음의 필수 산출물로 잡지 않는다.

**검증 묶음:**

1. 제어된 원천에 과거 1분 누락과 32일 중단을 각각 만들고, 원천이 최신 봉을 제공하는 조건에서 두 번의 수집 주기 안에 최신 조회가 회복되는지 확인한다. 과거 결측은 계속 노출되어야 한다.
2. 같은 복구 작업 중 재시작, timeout, 429/418, 잘못된 행을 주입한다. 작업 진행·중복 방지·대기시간·정정 이력의 일관성을 검증한다. 실제 거래소 호출 한도를 일부러 소진하지 않는다.
3. 과거 복구와 현재 수집 중 고정 `view_seq`로 여러 페이지를 읽어 중복·누락·버전 혼합이 없는지 확인한다.
4. 통합 후 BTC/ETH를 최소 24시간 관찰한다. 초기 제안 기준은 정상 원천·설정된 호출 예산 안에서 **봉 종료부터 조회 가능까지 지연의 99%가 120초 이내**, 원인 미분류 결측 0개다. 장애 구간은 별도로 전부 보고하고 정상 분포에서 제외한 구간·이유도 남긴다. 이는 운영 SLA나 현재 달성한 수치가 아니다.
5. 관찰 결과에 요청 횟수·원천 오류·지연 분포·복구 소요·DB/WAL 증가량을 기록한다. 24시간 경과만으로 완료 판정을 내리지 않는다.

조회 가능 지연은 commit 전의 `recorded_at_ms`로 계산하지 않는다. commit 후 실제 API에서 레코드를 확인한 관측 시각으로 측정하고, 검증 클라이언트의 조회 주기 때문에 포함되는 측정 지연도 함께 기록한다.

### 9.3 M2a — 확정 펀딩 한 종류를 끝까지 연결

- 후보 ID: `derivatives.funding.settled`. 원천의 정산 사건과 현재 예상 펀딩은 별개 계열로 유지한다.
- BTC/ETH의 최근 30일을 작은 검증 범위로 잡아 원천 응답 → 정확한 수치 → 원본/revision 저장 → latest/range → 화면의 펀딩 표까지 연결한다.
- 정산 시각·비율·관련 가격·원천 사건 종류를 보존한다. 동일 시각의 다른 사건이 하나의 revision으로 덮이지 않도록 실제 응답과 키를 먼저 대조한다.
- 봉의 2분 freshness나 1분 슬롯 완전성 규칙을 재사용하지 않는다. 펀딩의 정산 일정·발표 대기·마지막 조회 성공을 구분하며, 과거 일정을 모르면 완전성을 단정하지 않는다.
- 완료 기준은 원천 대조, 부호·정밀도, 페이지 경계, 재수집·정정, 최근 정산 이후 수집과 재시작 검증이다. 예상 펀딩·규칙의 과거는 확정 이력으로 복원하지 않는다.

### 9.4 M2b — 현재 OI와 공식 기간 통계를 각각 제공

| 계열 후보 | 보유할 의미 | 과거에 대해 말할 수 있는 범위 |
|---|---|---|
| `derivatives.open_interest.snapshot` | 직접 관측한 현재 OI, 초기 수집 주기 약 1분 | 수집 시작 이후 실제 관측 이력. 중간의 모든 변화를 확보한 것은 아님 |
| `derivatives.open_interest.statistics.5m` | 원천이 제공하는 5분 통계 | 원천 제공 기간과 실제 보유 구간만. snapshot과 이어 붙이지 않음 |

정의·단위·시각 의미를 확인한 뒤 같은 조회 API와 화면의 데이터 선택기에 추가한다. 두 계열의 값이 가까워 보여도 서로 대체하거나 빈 구간을 보간하지 않는다. 사라지는 무료 과거는 M2 착수 시 제한된 범위부터 확보하되, 미지원 기간을 가능하다고 표시하지 않는다.

**정밀도는 M2 착수 전 결정할 사항이다.** 기존 프로젝트의 OI ×10^4 규칙으로 원천 모든 유효숫자를 담을 수 있는지 확인한다. 담을 수 없는 값은 조용히 반올림하거나 잘라내지 않는다. 원본을 정확히 보존하고 필드별 수치 계약을 별도 확정한 뒤 지원을 선언한다. M1 가격·수량 계약이나 기존 UDP 규격을 자동 변경하지 않는다.

M2 원천 계약 재확인(2026-09-16): 펀딩 이력의 시간 경계는 양 끝 포함이며 `rateType` 필드가 있다. 조정된 펀딩 규칙 조회는 전체 과거 일정이 아니다. 현재 OI와 기간 통계는 별도 endpoint이며, 통계 이력은 최근 1개월·최소 5분이다. 통계 예시에 소수 8자리가 있으므로 기존 OI 정밀도를 그대로 가정할 수 없다. 이 제약은 [Binance 공식 Market Data](https://developers.binance.com/en/docs/catalog/core-trading-derivatives-trading-usd-s-m-futures/api/rest-api/market-data)의 Funding History/Info, Open Interest/Statistics에서 확인했다. 새 수집 코드 작성 전 실제 소량 응답과 다시 대조한다.

### 9.5 이후 통합 API를 완성하는 작업

| 순서 | 사용자에게 보이는 결과 | 선행 조건·검증 |
|---|---|---|
| M3 준비 작업 | 미보유 기간 요청에 준비 가능 여부·진행 상태·작업 ID 반환 | M1.1 작업 기록·호출 예산 재사용. 명시적 준비 옵션/요청에서만 작업 생성하고 기존 조회는 조회 의미 유지 |
| M3 시점·PIT | 특정 시점 조회와, 보존된 범위에서 당시 이용 가능한 revision 조회 | 공개 시각을 모르면 모른다고 표시. 로컬 조회 가능 시각·시계 역행·재시작 경계를 정의하고 각 판단 시점의 미래정보 혼입 검증 |
| M3 운영 | 용량 경보·보관 정책·백업/복구·장기 관찰·호출 예산 | 원본/revision 증가 실측, 복구 연습, 거래소/IP 공유 한도 확인. 관측 증거 없이 저장소 전환을 선행하지 않음 |
| M4 소비자 1개 | 연구 코드가 같은 API로 과거와 현재를 사용 | 봉부터 시작해 검증된 계열 추가. 고정 view 재현, stale/결측 거부, 시점 누출 검증 후 비교 실행. 즉시 운영 전략 전환하지 않음 |
| M5 데이터·거래소 확대 | Mark/Index/Premium 및 전략에 필요한 다음 계열, 두 번째 거래소 | 데이터별 단위·시각·지원 범위와 API 호환성을 검증하며 한 종류씩 추가 |
| M6 구독 판단 | 필요하면 변경분 조회나 스트림·UDP 추가 | 소비자 수·실측 지연·요청량으로 결정. 도입 시 유실·재접속·정정 복구 검증 |

### 9.6 작업을 나누고 검토하는 방법

한 묶음은 **계약 확정 → 구현 → 장애/원천 대조 → 화면에서 확인 → 결과 기록** 순서로 끝낸다. 계약을 정한 후 저장·스케줄링과 원천/API 작업의 파일 소유권을 나눌 수 있다. 검증은 작성자와 다른 담당이 결과를 확인한다.

지금 바로 시작할 다음 묶음의 종료점은 **M1.1의 최신 수집 지속성과 복구 상태를 화면에서 확인하는 것**이다. 그 결과를 검토한 뒤 펀딩, 이어서 OI로 넘어간다. 구독 방식·전체 거래소 수·운영 배치 위치를 한 번에 결정하지 않아도 이 순서로 진행할 수 있다.
