# data-service 수집 설계 검토안 — feed와 그 과거 (2026-09-28)

사용자 피드백을 받기 위한 문서다. data-service가 sicadb에 무엇을, 어디서, 얼마나 빨리 넣는지를 정리했다. 구현은 아직 하지 않았다. sicadb 저장 쪽이 마무리되고 사용자가 지시하면 시작한다.

- **근거**
  - 2026-09-27~28 원천 전수 조사(영역별 Opus 조사 에이전트 11개).
  - 한도·지연 실측: 경계 4개에서 약 19초 간격 폴링, WS 캡처.
  - 과거·실시간 대조: 행 단위 비교.
  - 결론을 바꾸는 주장은 따로 다시 호출해 확인했다.
- **표기**
  - **실측**: 직접 호출해 확인했다.
  - **문서**: 공식 문서만 근거다.
  - 지연은 원천의 기준 시각(구간 끝·봉 마감)에서 처음 받을 수 있었던 시각까지의 시간이다.

## 0. 먼저 보셔야 할 것

1. **봉은 WS로 받는다.** 5개 거래소 모두 봉 마감 뒤 0.1~0.9초 안에 확정 봉이 온다. 값은 REST와 같다(실측). REST는 끊긴 구간을 채울 때만 쓴다.
2. **한 IP로 제시간에 못 받는 것은 사실상 Binance `/futures/data` 하나다.**
   - 대상은 OI 통계·top trader 비율 2종·전체 계정 비율·taker·basis 6종 × 369종목(5분 2,214건)이다. 한도는 IP당 5분 1,000건이다.
   - 한도가 경로마다 따로인지 전부 합쳐서인지 공식 답이 없다. 넘겨서 시험하면 같은 IP를 쓰는 feeding(실거래 시세)까지 차단될 수 있다.
   - **해결안**: 이 수집만 도쿄의 저가 서버(고정 IP, 월 5~15달러)로 옮긴다(§3). 사용자 결정이 필요하다.
3. **과거 원천과 feed는 대부분 같은 데이터다.** 다만 몇 가지는 다르거나 같게 만들 수 없다(§4).
   - Binance taker 비율: 과거(Vision)와 실시간(REST)이 약 1e-4 수준으로 다르다.
   - Gate OI: 조회할 때마다 과거 값이 통째로 움직인다.
   - OKX 비율 통계: 최신 행은 잠정값이라 확정된 뒤에만 쓴다.
4. **무료 키 가입이 필요하다(§7).** Coinalyze, FRED, ECOS, TronGrid.

## 1. 원칙 (사용자 결정 2026-09-27~28)

- **feed가 기준이다.** feed는 상시 수집이고 실거래에 쓴다. 과거 적재는 feed가 받는 데이터의 과거를 구할 수 있는 만큼 구하는 것이다.
- **과거와 실시간은 같은 데이터여야 한다.** 값·시각표·정밀도가 다른 과거 원천은 그대로 섞지 않는다.
- **data-service의 몫은 시세가 아닌 데이터다.**
  - 호가·체결·WS 실시간 시세·청산 틱은 feeding이 한다.
  - data-service는 다른 차원·다른 시각에서 시장을 보는 데이터를 모은다. 거래소 밖 데이터가 특히 중요하다.
- **feed는 늦으면 안 된다.** 원천이 공개한 직후에 받는다.
- **원천이 과거를 주지 않거나 짧은 창만 남기는 데이터도 feed에 넣는다.** 그 경우 feed가 쌓는 것이 곧 과거다.
- **값은 고정 스케일 i64다**(Decimal 금지, §5).
- **넣지 않는 것**: BitMEX(폐쇄), 호가 아카이브, 체결 틱.
- **저장**: sicadb에 적재까지만 한다. 읽기는 읽는 쪽이 sicadb로 한다.
  - 실시간은 data-service 전용 feed handler가 sicadb producer로 쓴다.
  - 과거는 sicadb `Backfill`로 같은 archive에 넣는다.

## 3. 한 IP로 부족한 곳 — Binance `/futures/data`

### 3.1 문제

- 모든 PC가 공인 IPv4 하나로 나간다. IPv6는 없고, Binance는 IPv6 주소를 내놓지 않는다.
- 이 IP를 feeding(실거래 시세, Binance REST 가중치 사용)과 함께 쓴다.
- 필요량은 6종 × 369 = 5분 2,214건이다(OI 현재값은 다른 풀).
- 한도는 «IP당 5분 1,000건»이다.
  - 문서는 경로마다 따로 적었다. 반면 funding 문서는 «공유»라고 명시한다. 이 차이는 경로별 한도를 시사한다.
  - 공식 답은 없다. 응답 헤더로도 볼 수 없는 별도 카운터다.
- 한도가 합산이면 불가능하다. 경로별이면 경로당 37%로 들어가지만, 20% 안전선은 넘는다.
- 차단의 대가가 크다. 429를 무시하면 418 차단(2분~3일)이 나고, 같은 IP의 feeding까지 멈춘다.
  - 실전 사례(TRAVIS-WORLD): 같은 IP에서 과거 적재를 함께 돌리다 `-1003` 차단을 당해 운영 수집이 멈췄다. 이후 별도 IP로 분리했다.
  - 이 사례에서 한도 초과 응답은 429가 아니라 «HTTP 200 + code -1003»으로 오기도 했다.

### 3.2 다른 곳의 방식

- **cryptofeed·tardis 실시간·nautilus·freqtrade**: 비율을 실시간으로 받지 않거나, OI 현재값만 폴링한다.
- **tardis(과거 수집)**: 도쿄에서 비율 4종을 1분마다 받는다. 한 IP로는 불가능한 양이라 여러 IP로 추정한다.
- **Binance 개발자 커뮤니티**(2024-09): «임대 서버의 고정 IP를 여러 개 쓰는 것은 괜찮다. 익명화·로테이팅 프록시는 안 된다.» 공식 직원 답변인지는 확인하지 못했다.
- **유료 벤더**(CoinGlass $29~699/월 등): 결국 같은 REST를 긁는다. 지연 = Binance 공개 지연 + 벤더 폴링이다. 실시간의 표준 해법은 자체 수집이다.
- **WS 대안**: 비율 3종은 WS가 없다. taker를 WS 봉으로 만들면 값이 다르다(§4). OI 5m 행은 경계 시점의 현재값과 같다(R1 실측). basis는 WS 근사가 정의와 맞는지 검증이 필요하다.

### 3.3 선택지

| 안 | 내용 | 비용 | 지연 | 위험 |
|---|---|---|---|---|
| **A (권장)** | `/futures/data` 수집만 도쿄 저가 서버(고정 IPv4) 한 대로 옮긴다. 거기서 공유 여부를 1회 시험해 확정한다 | 월 5~15달러 | 원천 공개 직후(T+2~3분) | feeding과 차단 위험 분리. Binance 커뮤니티 답변상 허용 |
| B | 집 IP에서 20% 계층 스케줄: 상위 20~100종목은 5분마다, 나머지는 15분~2시간마다 | 0 | 상위만 제시간, 나머지는 늦음 | 한도가 합산이면 대부분 늦다 |
| C | 한도가 경로별임이 확인되면 집 IP에서 전 종목 5분(경로당 37%) | 0 | 제시간 | 20% 안전선을 넘는다. 차단 시 feeding도 멈춘다 |
| D | 유료 벤더 | 월 수백 달러 | 공개 지연 + 벤더 주기 | 실시간 이점 없음 |

- 폴링 방식(A·B·C 공통): 구간이 끝나면 BTCUSDT로 공개됐는지 먼저 확인한다. 공개됐으면 전 종목을 `limit=1~2`로 한 바퀴 돈다.
- 목표 시각: OI·비율은 T+150초와 T+180초, taker는 구간 끝+210초, basis는 끝+40초.
- 429·418·«200 + -1003»은 모두 한도 초과로 처리하고, Retry-After를 지킨다.

## 4. 과거와 feed가 같은 데이터인가 (행 단위 실측)

| 항목 | 결과 |
|---|---|
| Binance OI(Vision ↔ REST) | **같다.** 277/277행이 끝자리까지 일치한다. 시각표만 REST = Vision + 5분이다(REST는 찍은 시각, Vision은 구간 시작) |
| Binance top trader 계정·전체 계정 비율 | **같은 데이터다.** REST 비율은 롱·숏 비중을 소수 4자리로 반올림한 뒤 나눈 값이다(예: 0.5658÷0.4342=1.3031). 그래서 Vision(반올림 전 8자리)과 최대 약 2e-4 다르다. 시각표 차이는 OI와 같다 |
| Binance top trader 포지션 비율 | REST = Vision을 4자리 반올림한 값. 반올림 경계에 걸린 행이 하루 1~4개 있다 |
| **Binance taker 비율** | **다르다.** 상대오차 평균 6e-5, 최대 3.2e-4. 반올림으로 설명되지 않는다. 예: BTCUSDT 2026-09-26 00:25 — Vision 0.258993, REST 104.009/401.462 = 0.259076(재확인). 시각표는 같다 |
| Binance taker(WS 봉 ↔ REST) | 다르다. 277구간 중 95개가 0.01 BTC 넘게 다르다. taker는 REST·Vision으로만 받는다 |
| Binance 봉 5m(Vision ↔ REST ↔ WS) | **같다**(선물·현물 288/288, WS 확정 봉 = REST) |
| Binance funding(Vision ↔ REST) | **같다**(2026-08 BTC·ETH 93/93, ms 오차까지 일치) |
| Binance mark·index·premium 5m(Vision ↔ REST) | **같다**(288/288) |
| Binance mark 1m(WS `markPrice@1s` → OHLC ↔ REST) | **같다**(7/7분, 8자리) |
| Binance index 1m(WS `i` → OHLC ↔ REST) | 다르다(6/7분). REST 샘플이 약 1초 어긋난다 → index는 REST로 받는다 |
| Bybit 봉(WS ↔ REST), OI(WS 경계 직전 값 ↔ REST 행) | **같다** |
| OKX 봉(WS ↔ REST ↔ history ↔ bulk module 2) | **같다.** bulk 파일의 날짜 경계는 HKT(UTC+8)다. 숫자 문자열 형식만 다르다(«84880.0»/«84880») |
| OKX funding(bulk module 3 ↔ REST) | 같다(6/6). 파일 경계는 HKT |
| OKX rubik(잠정 ↔ 확정) | 최신 행은 잠정값이라 계속 갱신된다. 예: taker 00:25 행이 00:31에는 매수 18539.28, 최종은 20017.11이었다. **다음 행이 생긴 뒤에만 확정값으로 받는다** |
| OKX rubik OI ↔ WS OI | rubik 행은 WS OI를 1~2분 간격으로 샘플링한 값이다. WS로는 재현할 수 없다 → rubik을 받는다 |
| Upbit 1m(WS ↔ REST), Deribit DVOL 1m(WS → OHLC ↔ REST) | **같다** |
| **Gate contract_stats OI** | **같게 만들 수 없다.** 조회할 때마다 과거 행 전체의 OI가 같은 폭으로 움직인다(재확인: 3초 간격 두 조회에서 +4,578). 최신 행은 1분 값이다 |
| 미확인 | Kraken·Bitfinex·Bithumb·Coinone의 과거↔실시간, Bybit·Deribit·OKX funding의 WS↔정산값 |

**처리 방안(피드백 요청)**
- **시각표**: 모든 5분 계열을 «구간 시작»으로 통일한다(Binance OI·비율 REST는 5분을 뺀다). 원천이 준 시각도 함께 저장한다.
- **Binance 비율 정밀도**
  - 과거(Vision)는 8자리, 실시간(REST)은 4자리 비중에서 계산된 값이다.
  - 안 1: 둘 다 그대로 저장하고, 출처 열로 구분한다.
  - 안 2: 과거도 REST와 같은 방식(비중 4자리 반올림 → 비율)으로 변환한 열을 따로 둔다. 과거로 만든 전략이 실거래에서 같은 값을 보게 된다.
- **Binance taker 비율**: 실시간은 REST, 과거 30일 초과분은 Vision뿐이다. 약 1e-4 차이를 감수할지, 30일 이전 taker는 쓰지 않을지 정해야 한다.
- **Gate OI**: feed만 쌓고 과거는 쓰지 않는다(L/S·청산은 사용).

## 5. 값 표현 — 고정 스케일 i64 (결정됨)

- 넘겨받는 1,133종목의 일봉 전 이력을 실측해 스케일을 정했다. 봉 테이블은 거래소마다 나눠 스케일을 따로 둔다.

  | 테이블 | 가격 | 거래량 | 거래대금 |
  |---|---|---|---|
  | binance-futures | ×10^10 | ×10^3 | ×10^8 |
  | binance | ×10^10 | ×10^6 | ×10^8 |
  | bybit-linear | ×10^10 | ×10^3 | ×10^7 |
  | okx-swap | ×10^10 | ×10^4 | ×10^6 |
  | okx-spot | ×10^10 | ×10^8 | 담지 않음 |

- **잃는 것**: OKX 현물 거래대금(전 종목), OKX 현물 PEPE·SHIB·BONK 거래량, Binance 유통량 필드. 나머지는 손실이 0이다.
- **여유가 작은 곳**: 일봉 Binance 선물 BTC 거래대금은 한도까지 1.3배, OKX PEPE 거래량은 2배. 넘치면 값을 자르지 않고 그 필드만 null로 두고 알린다.
- Binance 5분 계열: OI ×10^4, OI 가치 ×10^8, taker 거래량 ×10^4, 비율·funding ×10^8. 369종 실측에서 손실 0이다.
- 새 원천(거래소 밖 포함)은 적재 전에 같은 방식으로 자릿수를 실측해 스케일을 정한다.

## 6. 시각·버전 규칙 (모든 feed 공통)

- 원천이 준 기준 시각, 공개(처음 본) 시각, 받은 시각을 구분해 저장한다.
- 값이 나중에 바뀌는 원천은 덮어쓰지 않고 버전으로 쌓는다. 읽는 쪽은 «T 시점에 알던 값»을 고를 수 있다. 해당 원천: Coin Metrics, FRED, DefiLlama, Farside, 공지, OKX rubik 잠정값, ForexFactory.
- 거래소 파일의 날짜 경계를 원천마다 확인한다(OKX bulk는 HKT, 국내 일봉은 KST 또는 UTC).
