# Rust Arrow 변환기: NAS·워크스테이션 실측 비교

측정·갱신일: 2026-09-16 (KST)

**실제 변환기를 Rust 실행파일로 다시 만들었습니다. NAS 2코어에서는 Python 대비 처리량이 2.17배, 워크스테이션 8개 병렬 작업에서는 1.12배였습니다.** 워크스테이션은 원격 파일 입출력이 대부분을 차지해 개선 폭이 작았습니다. 소규모 실측이며 전체 이관 시간 예측은 아닙니다.

**전체 처리 시간**

동일한 8개 파일, 입력 203.03 MB·533,504행입니다. 변환 작업 시작부터 출력 저장까지의 경과 시간에 **NAS의 최종 파일 SHA-256 재검증** 시간을 더했습니다. 전송·동기화·모든 컬럼 재검증을 포함합니다.

| 실행 방식 | 1회 | 2회 | 3회 | 중앙값 | 입력 처리량 |
|---|---:|---:|---:|---:|---:|
| NAS · Python · 2프로세스 | 18.45초 | 20.80초 | 19.40초 | **19.40초** | 10.47 MB/s |
| NAS · Rust · 2스레드 | 8.95초 | 10.33초 | 8.46초 | **8.95초** | 22.69 MB/s |
| 워크스테이션 · Python · 8프로세스 | 9.21초 | 9.65초 | 10.79초 | **9.65초** | 21.03 MB/s |
| 워크스테이션 · Rust · 8스레드 | 8.61초 | 8.05초 | 8.74초 | **8.61초** | 23.59 MB/s |

처리 시간은 NAS 약 53.9%, 워크스테이션 약 10.8% 감소했습니다. 공유 저장소 부하·캐시 변동을 포함하므로 특히 워크스테이션의 작은 차이를 언어 자체의 확정적인 개선율로 해석하지 않습니다.

**구현과 최적화**

실제 입력 읽기, 42/46개 피처 벡터의 컬럼 분리, 무압축 Arrow IPC FILE 저장, 원본·출력 SHA-256, 전체 컬럼 재검증, 병렬 실행과 출력 전송은 **Rust**입니다. 변환 실행파일은 Python을 호출하지 않습니다. 추가된 Python은 기존 구현과의 비교 실행·독립 검증·공통 NAS 최종 검증·보고서 집계용입니다.

Rust 1.93.1, Apache Arrow Rust 59.3.0, Rayon, ring 0.17.14 SHA-256을 사용했습니다. Windows exe와 Linux musl 정적 실행파일을 release·opt-level 3·thin LTO로 빌드했습니다.

- 파일 단위 컬럼 버퍼에 누적해 작은 입력 배치마다 46개 배열을 만드는 비용을 줄였습니다. 완성된 버퍼는 Arrow 배열로 복사 없이 넘깁니다.
- 전치 함수를 세 가지로 비교한 뒤 **32행 타일 방식**을 기본으로 정했습니다. 정상 자료에서는 별도 결측 마스크를 만들지 않습니다.
- 누적한 컬럼을 크게 해시합니다. 출력은 한 번 재읽은 버퍼로 컬럼 재검증과 파일 SHA-256을 함께 계산합니다.
- SHA-256 규약을 유지하면서 실제 장비에서 빠른 ring 구현을 선택했습니다. 검증을 없애거나 약한 해시로 바꾸지 않았습니다.
- 출력은 4MiB 버퍼로 기록·동기화합니다. 결과 JSON은 직렬화 후 한 번에 써서 SMB의 수많은 작은 쓰기를 없앴습니다. 원본 목록 확인과 변환 전 상태 확인을 합쳐 중복 파일 정보 조회를 줄였습니다.

| 단위 함수 측정 | NAS | 워크스테이션 |
|---|---:|---:|
| 500행 전치: 컬럼 순회 → 32행 타일 | 2.35 → 3.48 GB/s | 13.44 → 14.48 GB/s |
| 65,536행 전치: 컬럼 순회 → 32행 타일 | 0.36 → 1.30 GB/s | 1.83 → 3.59 GB/s |
| SHA-256: 참조 SHA2 → ring | 66.62 → 113.29 MB/s | 209.23 → 390.86 MB/s |

전치는 이미 할당한 메모리에서 크기별 30회, 해시는 32MiB를 10회 처리했습니다. 파일 입출력이 없는 단위 함수 측정이며 전체 변환 속도와 다릅니다.

**Rust에서 남은 병목**

각 실행의 8개 파일 단계 시간을 합한 후 3회 중앙값을 구했습니다. **병렬 작업의 누적 시간이므로 위의 실제 경과 시간과 다릅니다.** 단계별 중앙값을 더해 전체 경과 시간으로 해석할 수 없습니다.

| 단계별 누적 시간 | NAS · Rust 2스레드 | 워크스테이션 · Rust 8스레드 |
|---|---:|---:|
| 원본 읽기 | 1.34초 | 23.23초 |
| 원본 SHA-256 | 1.92초 | 0.55초 |
| Arrow 해석·컬럼 분리 | 0.72초 | 0.13초 |
| 컬럼 검증값 생성 | 2.20초 | 0.59초 |
| 출력 쓰기·동기화 | 2.76초 | 0.26초 |
| 출력 재읽기 | 0.30초 | 0.14초 |
| 전체 컬럼 재검증 | 2.67초 | 0.68초 |
| 출력 SHA-256 | 1.94초 | 0.53초 |
| 워크스테이션 → NAS 전송·동기화 | 0.00초 | 11.01초 |

NAS는 해시·검증과 파일 동기화의 비중이 큽니다. 워크스테이션은 원격 읽기와 NAS로의 전송이 지배적입니다. 표에 없는 경로·파일 정보 확인도 실제 처리 시간에는 포함됩니다. 공통 최종 NAS 재검증 약 2초도 전체 시간에 포함했습니다. 네트워크 링크·SMB 서버 CPU·저장장치 대기 각각의 기여도를 분리한 측정은 아닙니다.

**정확성 검증**

- 최신 비교 12회·96개 파일 변환에서 원본 SHA-256, 48개 컬럼의 값 비트·null·행 순서 검증값, 행 수·시각 범위가 Python 결과와 일치했습니다.
- Rust 출력은 두 운영체제와 반복 실행에서 같은 파일 SHA-256을 얻었습니다. **Python과 Rust의 물리적 파일 바이트는 다릅니다.** 값·결측·스키마 의미는 같으며 Rust writer의 유효성 비트맵 기록 등 배치 차이가 있습니다. 8개 출력 합계는 Python 201,748,688바이트, Rust 204,969,264바이트로 Rust가 약 1.6% 큽니다.
- 합성 자료 4종 × 전치 구현 3종으로 42/46 폭 혼합, null, NaN payload, 음의 0, 무한대, 빈 입력, 출력 배치 경계를 검증했습니다. PyArrow로 Rust 결과를 독립적으로 재읽어 비교했습니다.
- Rust 단위 테스트 4개·Clippy를 통과했습니다. 참조 해시 빌드에서도 4개 테스트가 통과했습니다. 목록 작성 후 크기가 달라진 원본은 실패하며 성공 결과를 남기지 않는 것도 확인했습니다.
- 원본은 읽기 전용, 결과는 별도 시험 경로를 사용했습니다. 운영 Python 소스 26개 해시는 승인된 이관 기준과 일치했습니다.

**측정 조건과 한계**

입력은 Binance Futures·Bybit Linear의 BTC·ETH, 2026-08-10·11, 총 8개 파일·203,031,976바이트입니다. 출력은 타임스탬프 + 46개 피처 + 원래 피처 폭, 총 48컬럼의 무압축 IPC FILE입니다.

NAS는 Synology DS1815+·Atom C2538 4코어·RAM 약 16GB입니다. Docker의 `--cpuset-cpus=2,3 --memory=2g`를 적용하고 변환·최종 검증에서 CPU 허용 목록 2–3을 확인했습니다. 이는 해당 작업의 코어를 2개로 제한하며 **NAS 전체 CPU 사용률 50% 제한은 아닙니다.** 해당 커널은 CFS CPU quota를 지원하지 않습니다. [Docker 공식 CPU 제한 설명](https://docs.docker.com/engine/containers/resource_constraints/#cpu)

워크스테이션은 Xeon Platinum 8173M × 2, 56물리코어·112논리CPU, RAM 약 768GiB, NAS 연결은 1Gbps입니다. 코어 고정 없이 작업 수를 8개로 설정했습니다. Python은 프로세스, Rust는 Rayon 스레드로 병렬화했습니다. Python 기준은 NAS 3.12.14·워크스테이션 3.12.10, PyArrow 25.0.1·NumPy 2.5.3이며 수치 라이브러리 내부 스레드는 1개였습니다.

진행 중인 전체 이관과 NAS 서비스를 유지했고 캐시를 비우지 않았습니다. 먼저 머신별로 Python/Rust 순서를 번갈아 각 3회 측정했습니다. 이후 중복 파일 정보 조회를 정리한 최종 Rust 빌드만 머신별로 3회 다시 측정해 위 표에 사용했습니다. **최신 Rust와 Python 기준은 시간상 교차 배치된 실험이 아니며 부하 변화의 영향을 받습니다.** 이전 Rust 빌드에서도 NAS 약 2.06배, 워크스테이션 약 1.07배라는 같은 방향의 결과를 얻었습니다.

프로세스·스레드 풀 생성은 포함했습니다. 패키지 설치, 컨테이너·SSH·WinRM 시작/종료, 측정 사이 대기, 로그 수집, 결과 JSON 게시 시간은 제외했습니다. 최종 Rust의 워크스테이션 결과 JSON 게시는 약 0.01~0.11초였으며 별도 기록했습니다. NAS 최종 SHA-256 검증은 양쪽에 같은 코드를 적용했습니다. 운영에서는 변환과 NAS 검증이 겹칠 수 있습니다.

**이 결과로 전체 4.75TB의 완료 시간을 외삽하지 않습니다.** 전체 자료는 파일 크기·배치 구조가 다양하고 기존 이관은 16개 프로세스로 실행 중입니다. Rust의 파일당 입력 상한은 기본 256MiB이며 초과 입력은 실패합니다. 전체 이관 연결에는 파일 크기 분포, 병렬 작업 수별 메모리, 재개·불변 객체 게시·제어 절차를 함께 검증해야 합니다.

**운영 상태**

Rust 변환기 구현·최적화·비교를 완료했습니다. 시험 컨테이너와 변환 프로세스는 종료했고 기존 전체 이관은 유지했습니다. 기존 이관·일일 스케줄러를 Rust로 교체하지 않았습니다. 원본, 기존 인프라 코드, 데이터 등록도 변경하지 않았습니다.

측정 원본·실행파일 해시·단계별 시간·검증 기록은 로컬에 보존했습니다. 공개 문서에는 인증 정보, 내부 주소, 실제 로컬 경로와 원본 데이터를 포함하지 않았습니다.

# NAS 2코어 제한: Arrow 변환 실측 비교

측정일: 2026-09-16 (KST)

**NAS에서 2코어로 변환할 수 있습니다. 다만 이번 시험에서는 워크스테이션 8개 병렬 처리가 약 1.90배 빨랐습니다.** 같은 2개 작업 프로세스로 비교하면 NAS가 약 12.5% 짧게 걸렸습니다. 네트워크 왕복 제거 효과는 있었지만, NAS 이전만으로 전체 이관이 빨라진다고 판단할 결과는 아닙니다.

**전체 처리 시간**

같은 8개 파일을 방식별로 3회 처리했습니다. 아래 시간은 파일 변환 작업 시작부터 저장까지의 시간과, NAS에서 수행한 최종 파일 검증 시간을 더한 값입니다.

| 실행 방식 | 1회 | 2회 | 3회 | 중앙값 | 처리량 |
|---|---:|---:|---:|---:|---:|
| NAS · 2코어 / 2프로세스 | 19.08초 | 20.18초 | 19.81초 | **19.81초** | 10.25 MB/s |
| 워크스테이션 · 2프로세스 | 22.64초 | 22.60초 | 22.99초 | **22.64초** | 8.97 MB/s |
| 워크스테이션 · 8프로세스 | 10.99초 | 9.82초 | 10.41초 | **10.41초** | 19.50 MB/s |

**어디에 시간이 들었나**

아래는 각 실행에서 8개 파일에 걸린 시간을 합한 뒤, 3회의 중앙값을 구한 것입니다. 병렬 작업 시간이 겹치므로 위의 실제 경과 시간과 다릅니다. 각 행의 중앙값도 합계의 중앙값과 일치하지 않을 수 있습니다.

| 단계별 누적 시간 | NAS · 2프로세스 | 워크스테이션 · 2프로세스 | 워크스테이션 · 8프로세스 |
|---|---:|---:|---:|
| 원본 NAS → 워크스테이션 복사 | 해당 없음 | 12.86초 | 20.87초 |
| 원본 읽기·변환·쓰기·컬럼 검증값 생성 | 22.43초 | 4.30초 | 5.13초 |
| 변환본 전체 컬럼 재읽기·검증 | 3.04초 | 0.87초 | 0.90초 |
| 변환 파일 전체 SHA-256 계산 | 2.05초 | 0.58초 | 0.60초 |
| 변환본 워크스테이션 → NAS 복사·동기화 | 해당 없음 | 12.28초 | 13.34초 |
| 기타 파일 정보 확인·임시 파일 정리 | 0.01초 | 7.28초 | 10.25초 |

최종 NAS 파일 검증은 별도로 실행했으며 세 방식 모두 약 1.95초였습니다. NAS 방식의 원본 읽기와 파일 쓰기는 두 번째 행에 포함됩니다. 워크스테이션 방식에서는 두 번째 행이 로컬 디스크 작업입니다.

워크스테이션은 변환 계산 자체가 빨랐지만, 네트워크 파일 읽기·쓰기와 파일 정보 확인에 시간이 많이 들었습니다. 8개 병렬 처리는 그 대기를 겹쳐 전체 시간을 줄였습니다. NAS는 왕복 전송이 없어지는 대신 변환·검증 계산 시간이 길었습니다. 이 시험만으로 SMB 서버 CPU, 디스크, 네트워크 링크의 기여도를 각각 분리한 것은 아닙니다.

**측정 조건과 검증**

- 입력: Binance Futures·Bybit Linear의 BTC·ETH, 2026-08-10·11. 총 8개 파일, 203,031,976바이트(203.03 MB), 533,504행입니다.
- 출력: 기존 변환기로 만든 무압축 Arrow IPC FILE. 타임스탬프 + 피처 46개 + 원래 피처 폭, 총 48컬럼입니다. 한 묶음의 출력은 201,748,688바이트입니다.
- NAS: Synology DS1815+, Atom C2538 4코어, RAM 약 16GB. Docker에서 `--cpuset-cpus=2,3 --memory=2g`를 적용했습니다. 변환 및 최종 검증 프로세스 모두 실제 CPU 허용 목록이 `[2, 3]`임을 확인했습니다.
- 워크스테이션: Xeon Platinum 8173M × 2, 총 56물리코어·112논리CPU, RAM 약 768GiB, NAS 연결은 1Gbps입니다. CPU 코어 고정 없이 작업 프로세스 수를 2개 또는 8개로 설정했습니다.
- 양쪽 모두 PyArrow 25.0.1, NumPy 2.5.3, 동일한 변환 소스입니다. Python은 NAS 3.12.14, 워크스테이션 3.12.10입니다. 수치 라이브러리의 내부 스레드는 1개로 설정했습니다.
